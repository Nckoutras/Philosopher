# P0 — Critical blocker

## BUG-001 — Clean-browser Sign in is blocked by failure of “today’s mind”

**Type:** Confirmed functional defect  
**Area:** Authentication / welcome routing / content dependency  
**Where and when:** Production, clean cloud Chromium session, signed out; 14 September 2026, approximately 15:45 Greece time.

**Preconditions**

- No usable authenticated session in the browser.
- Daily-mind content fails to load.

**Reproduction**

1. Open https://thewiseroom.app in a clean browser.
2. Select **Sign in**.
3. Observe navigation to **/app/welcome**.
4. Wait for the daily-mind section.
5. Select **Try again** and then **Begin**.
6. Attempt direct navigation to the previously observed authentication route.

**Actual result**

- The page shows **“Could not load today’s mind.”**
- **Try again** does not recover or show meaningful progress/failure feedback.
- **Begin** does not open authentication.
- Direct authentication navigation returns to the broken welcome state.

**Expected result**

- **Sign in** must always open the email/OTP flow, independently of editorial or thinker-content APIs.
- Daily-content failure should show a fallback while authentication remains fully usable.
- **Try again** and **Begin** must perform their labelled actions and expose loading/error state.

**Evidence and frequency**

- One confirmed clean-browser occurrence with screenshot.
- Production incidence is unknown; forced-failure testing is required.

**Impact**

- New and returning signed-out users may be unable to enter the product.
- This blocks activation, paid-account usage and longitudinal QA.

**Implementation direction**

- Decouple auth initialization from daily-mind fetching.
- Add a content fallback and bounded retry.
- Prevent content errors from controlling auth routing.

**Acceptance tests**

- Clean browser → Sign in → email/OTP form loads while the daily-mind API returns 500, timeout and empty payload.
- A returning signed-out user can authenticate under the same forced failures.
- A returning authenticated user reaches the correct app destination.
- **Try again** and **Begin** never silently no-op.

**Type:** Confirmed functional defect  
**Area:** Authentication hydration / protected routing  
**Where and when:** Production authenticated session; observed on **/app/today** and **/app/self-portrait** during logged-in QA. Exact timestamp and browser build were not captured.

- Add an explicit auth-hydration state and defer route guards.
- Preserve and validate the intended destination.

**Acceptance tests**

- Hard refresh and direct-open tests pass for every protected primary route.
- Valid session restores the target; expired session signs in and then returns to it.
- No redirect loop occurs under slow auth-provider response.
