# 1. Core thesis

The Wise Room should not be understood as:

> a chat app plus a collection of rituals.

The target model is:

> **The chat engine is the continuous sensing/exploration layer. Memory is the shared intelligence layer. Insights detect meaning across time. Rituals transform accumulated knowledge. User confirmation/rejection feeds the result back into the system.**

In short:

**CHAT → REMEMBER → NOTICE → TRANSFORM → CONFIRM → LEARN → BETTER FUTURE CHAT/RITUALS**

The commercial goal is to create a product where a user can say:

> “The Room knows my history in a way it could not possibly have known me three months ago.”

That is the potential switching cost and long-term subscription value.

---

# 2. Why this matters

The main risk for an AI reflection product is novelty decay.

Users may initially enjoy:
- Socrates or Jung conversations,
- The Council,
- a beautiful Self Portrait,
- a shareable reflection artifact.

But novelty does not justify indefinite recurring payment.

The strongest defensibility is not the visible feature set. A competitor can copy personas, prompts, rituals and cards. What it cannot immediately copy is six or twelve months of:
- recurring dilemmas,
- decisions,
- beliefs,
- corrections,
- rejected interpretations,
- confirmed insights,
- shifts,
- prior Council outcomes,
- Sunday Letter correspondence,
- unresolved questions.

The Wise Room should therefore **accumulate this history and spend it intelligently across the experience**.

# 3. Current repo findings motivating this proposal

The latest teardown found:

### Conversation / memory
The chat engine already extracts concepts such as:
- belief,
- value,
- struggle,
- pattern,
- milestone,
- dilemma,
- aspiration.

Cross-conversation recurrence also exists.

But ordinary recall is still relatively naive:
- semantic top-k,
- weak deduplication,
- no meaningful decay,
- weak recency/importance weighting,
- weak conflict handling,
- limited provenance.

So the system stores history, but does not yet build a robust model of the person.

### Compounding exists, but unevenly
Real longitudinal value exists in:
- **You vs You**
- **Sunday Letter**
- **The Room noticed / recurrence**

But accumulated user history is under-used by major surfaces such as:
- Council,
- Self Portrait,
- Mirror,
- Counterview,
- Future Self.

### Council
Council is a strong decision instrument, but currently effectively memoryless. A month-12 Council does not know much more about the user than a day-1 Council.

### Self Portrait
The current Self Portrait is not yet a mature longitudinal user model. It needs answer-aware scoring, versioning and evolution before it can credibly function as a compounding asset.

# 4. Target architecture

## Layer 1 — Conversation Engine

Purpose:

> Explore the user's current experience and generate evidence.

Responsibilities:
- thinker-specific dialogue,
- immediate context,
- relevant prior recall,
- extraction of candidate structured signals,
- leave the system knowing the user slightly better after each meaningful conversation.

Chat is not required to resolve everything. Its second job is to create better longitudinal understanding.

---

## Layer 2 — Evidence / Memory Layer

Purpose:

> Preserve what is known, observed, hypothesized, rejected and changed.

This should distinguish epistemic status.

Suggested conceptual classes:

### USER_STATED_FACT
Something explicitly stated by the user.

### USER_STATED_BELIEF / VALUE / GOAL
Directly attributable to the user.

### OBSERVED_PATTERN
A system observation supported by repeated evidence.

### TENSION / CONTRADICTION
Two recurring pieces of evidence that appear to pull in different directions.

### AI_INTERPRETATION
An interpretation generated by a thinker, Council, Letter or ritual. **Not a fact.**

### USER_CONFIRMED_INSIGHT
An AI interpretation explicitly confirmed by the user.

### USER_REJECTED_INTERPRETATION
A conclusion the user explicitly says is wrong or does not fit.

### DECISION
A meaningful decision the user made.

### OUTCOME / FOLLOW-THROUGH
What happened after that decision.

### SHIFT
A real change between earlier and later positions.

Claude should simplify or merge these where sensible.

---

# 5. Non-negotiable principle: AI output must not automatically become user truth

Avoid this loop:

**AI interpretation → stored as fact → retrieved later → repeated by another thinker → repetition appears to validate the original hallucination.**

Preferred rule:

> **User statements are evidence. Repeated behavior may become an observation. AI interpretation remains interpretation. User confirmation can strengthen it. User rejection must reduce or remove its downstream influence.**

This needs first-class architectural support.

---

# 6. Layer 3 — Insight Engine

Purpose:

> Detect when accumulated evidence has become meaningful enough to surface.

Potential detections:
- recurring topic,
- repeated dilemma,
- unresolved question,
- contradiction,
- meaningful behavioral shift,
- repeated avoidance,
- repeated value conflict,
- decision without follow-through,
- change from an earlier position.

Avoid pseudo-clinical diagnosis.

The desired emotional beat is:

> **“The Room noticed something I had not realized was repeating.”**

---

# 7. Layer 4 — Ritual Router

Users should not need to know the internal feature taxonomy.

The system should increasingly know when a particular ritual is useful.

Examples:

- recurring unresolved dilemma → **Council**
- strong repeated belief → **Counterview**
- meaningful shift over time → **You vs You**
- several connected events this week → **Weekly Mirror / Sunday Letter**
- future commitment → **Future Self**
- long-term pattern accumulation → **Self Portrait update**

Routing must be restrained and editorial, not a noisy recommendation engine.

Preferred tone:

> “This may be worth taking to the Council.”

not:

> “Recommended feature: Council.”

---

# 8. Layer 5 — Rituals as transformation engines

Each ritual should have a clear **READ contract** and **WRITE contract**.

Do not dump all memory into every prompt.

Use the smallest relevant high-confidence context.

---

# 9. Council

## READ
Potential context:
- current dilemma,
- relevant user-stated facts,
- relevant values/goals,
- recurring tensions,
- prior related decisions,
- prior related Council outcomes,
- meaningful recent shifts,
- user-confirmed insights.

## THINK
Four independent thinker perspectives. Personal context should inform them without making all four converge.

## SYNTHESIZE
- real question,
- tension,
- disagreement,
- verdict,
- next move,
- uncertainty where appropriate.

## WRITE
Store:
- matter,
- evidence IDs used,
- perspectives,
- synthesis,
- next move,
- timestamp,
- user reaction,
- later outcome if known.

## Target behavior
A second Council on the same life territory three months later should know:
- what the first Council concluded,
- what the user accepted/rejected,
- what decision followed,
- what changed since.

---

# 10. Counterview

## READ
- belief submitted by the user,
- strongest evidence supporting it,
- potentially contradictory evidence,
- relevant confirmed/rejected interpretations.

## WRITE
- belief challenged,
- counterargument,
- evidence used,
- whether user accepted, rejected, partially accepted or modified the belief.

Strategic value:

> Create epistemic history: “What did I believe, and what changed my mind?”

---

# 11. You vs You

This is already one of the strongest longitudinal mechanics.

## READ
- older high-confidence signals,
- recent high-confidence signals,
- comparable themes,
- meaningful shifts,
- confirmed insights.

## WRITE
- changes observed,
- unchanged tensions,
- user-confirmed changes,
- rejected comparisons.

Strategic value:

> Prove that the product knows the user now in a way it could not have known them in week one.

---

# 12. Self Portrait — target role

Self Portrait should eventually become:

> **the slow-moving, uncertainty-aware portrait of the user's evolving tendencies.**

Possible sections:

### What appears stable
High-confidence patterns.

### What is changing
Signals that materially differ from earlier periods.

### What remains unresolved
Recurring tensions rather than forced conclusions.

### What surprised the Room
New evidence that contradicts the prior portrait.

### What is uncertain
Insufficient or conflicting evidence.

## READ
Potential inputs:
- quiz answers with actual weighted meaning,
- user-stated values,
- recurring patterns,
- long-term changes,
- confirmed insights,
- rejected interpretations,
- major decisions/outcomes,
- user corrections.

## WRITE
- versioned portrait state,
- evidence references,
- changes from previous version,
- confidence,
- user corrections.

Critical test:

> A six-month Self Portrait must contain meaningful information that could not have been produced from the user's latest five conversations.

---

# 13. Future Self

## READ
- current concern,
- goals,
- relevant values,
- current decision,
- confirmed patterns where useful.

## WRITE AT CREATION
- hoped-for outcome,
- fear,
- commitment,
- expected future date.

## WRITE AT OPEN
- what actually happened,
- what changed,
- whether the original fear/prediction was accurate.

Future Self can become strong longitudinal evidence rather than just a delayed message.

---

# 14. Sunday Letter — target role

Sunday Letter should become the **weekly orchestrator of the whole Room**.

Not:

> “summary of this week's chats.”

Instead:

> **“What happened across the user's intellectual life in the Room this week?”**

It should be able to consider:
- conversations,
- insights,
- Council,
- Counterview,
- You vs You,
- Future Self activity,
- relevant Self Portrait changes,
- write-backs,
- decisions,
- unresolved questions.

It should select the one or two things that mattered most.

The ideal Letter creates:
1. **recognition** — “yes, that was my week,”
2. **continuity** — “it remembers what came before,”
3. **re-entry** — “there is one thing worth opening again.”

Example final action:

> “There is one question you kept circling. Open it with Socrates.”

That sends the user back to Chat.

# 15. Layer 6 — User feedback as data

High-value artifacts should invite minimal, elegant feedback.

Possible actions:
- Rings true
- Not quite
- Not me
- Changed since then
- Keep this
- I acted on this
- Still unresolved

Do not overload the UX.

But user feedback is strategically valuable because it tells the system which interpretations actually fit.

# 17. Example

Suppose over six weeks the Room learns:

- user repeatedly wants more career responsibility,
- security repeatedly appears around career moves,
- user says title does not matter,
- recognition keeps resurfacing,
- relocation blocked an earlier decision,
- recently relocation seems less threatening.

User asks Council:

> “Should I accept this international role?”

A generic Council sees only the question.

A compounding Wise Room Council sees:

### Relevant facts
- Wants more international responsibility.
- Previously rejected a move partly due to relocation uncertainty.

### Repeated tension
- Growth vs security.

### Possible contradiction
- Stated indifference to title vs repeated recognition concerns.

### Recent change
- Relocation resistance appears weaker.

Suppose Council says:

> “The question may be less about whether this role is safe enough and more about whether you are willing to trade certainty for the identity you say you want.”

If the user presses **Rings true**, store it as a **user-confirmed insight**, not an objective fact.

Two weeks later Socrates can say:

> “Last time this came up, growth and security seemed to pull in opposite directions. Is that still the real tension?”

That moment is the product.

# 18. What NOT to do

## Do not load the whole memory store into every prompt
Causes cost, latency, noise and repetitive over-personalisation.

## Do not reference memory in every reply
Relevant memory should feel insightful, not creepy.

## Do not turn patterns into diagnoses
Prefer “this topic has appeared repeatedly” over psychological labels.

## Do not build a giant ontology before launch
We need the minimum architecture that produces commercial value.

## Do not build new rituals before existing rituals compound
Integration depth is the priority.

# 20. Retrieval principles

The long-term system should consider more than semantic similarity.

Claude should evaluate:
- relevance,
- recency,
- importance,
- confidence,
- user confirmation,
- source diversity,
- contradiction,
- duplication,
- type,
- ritual-specific context.

Objective:

> Retrieve the smallest set of evidence that makes the next interaction meaningfully more personal and accurate.

Avoid sophistication for its own sake.

---

# 21. Provenance

Strong claims about the user should preserve:
- where they came from,
- when,
- whether the user said them,
- whether AI inferred them,
- whether the user confirmed or rejected them.

The UI need not expose all of this, but the system should retain it.

This is important for:
- correction,
- deletion,
- trust,
- debugging,
- explainability,
- preventing hallucination loops.

---

# 22. Memory hygiene

Need a strategy for:
- duplicates,
- stale facts,
- conflicting evidence,
- evolving views,
- source weighting,
- temporary states,
- permanent facts,
- user corrections.

Important principle:

> **New evidence should not silently overwrite history.**

Example:

January: “I would never move abroad.”  
September: “I would move for the right role.”

Correct representation:

> The position changed.

The change itself may be the insight.

---

# 23. Ritual outcomes should matter later

Rituals should create state, not just content.

### Council
Decision tension, next move, user reaction.

### Counterview
Belief tested and retained/modified/rejected.

### You vs You
Shift detected and confirmed/rejected.

### Future Self
Commitment and later outcome.

### Self Portrait
Stable/evolving portrait state.

These outputs should influence later experiences when relevant.

---

# 24. UX principle — one Room, not many features

Bad UX:
- Use Council
- Use Counterview
- Use Self Portrait

Better UX:

> “You have come back to this three times. Would you like four minds to weigh it?”

> “You sound more certain about this than you did two months ago. Compare the two?”

> “You have stated this belief in different forms several times. Doubt it?”

The rituals should feel like **capabilities of The Room**, not a toolbox menu.

# 25. Success tests

### Week 1
Does the thinker feel distinct?

### Week 3
Does the Room remember something relevant?

### Month 2
Does it detect a pattern the user recognizes?

### Month 3
Can a ritual use history to produce a materially better output?

### Month 6
Can the product show genuine change over time?

### Month 12
Would switching to a generic AI mean losing something personally valuable?

Central test:

> **Can a six-month account produce meaningfully better reflection than a two-week account, even if both use the same base LLM?**

If yes, the product compounds.

---

# 26. Cost / latency constraint

Do not solve personalisation by inserting huge history into every call.

Explicitly evaluate:
- retrieval cost,
- token cost,
- latency,
- background vs synchronous processing,
- caching,
- heavy-user exposure.

The solution must remain compatible with a consumer subscription at the Wise Room price point.

---

# 27. Privacy / safety

A stronger memory system creates more value and more risk.

Evaluate:
- deletion propagation,
- correction propagation,
- GDPR erasure,
- export,
- sensitive-memory handling,
- accidental resurfacing,
- multilingual safety,
- user visibility/control.

A powerful memory system needs equally strong user control.
